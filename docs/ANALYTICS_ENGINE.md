# ANALYTICS_ENGINE.md — Block 03

The measurement engine behind the brief's chain: **DATOS → EVENTOS →
MÉTRICAS → READ MODELS → API**. No visual dashboard in this block — see
docs/REPORTING.md for the API surface it's ready to feed.

## Event taxonomy audit

Block 01/02 already had 12 event names on `interaction.event_name`. This
block reviewed them against the brief's minimum list (all 12 already
present) and its "consider adding" list (`OUTBOUND_CLICK`,
`PRODUCT_VIEW`, `OFFER_VIEW`, `CONTACT_CREATED`, `LEAD_CREATED`),
migrated in `0003_analytics_engine.sql`:

| Event | Fires when | Generated by | Metadata / entity | Analytical purpose |
|---|---|---|---|---|
| `page_view` | Any route render, no attribution signal in the URL | `PageViewTracker` (client) → `/api/track` | — | Which pillars get discovered. **Newly persisted this block** — Block 02 deferred it as "better served later"; this is that later. |
| `landing_view` | A route render whose URL carries a fresh utm_*/qr signal | `PageViewTracker` (client) → `/api/track` | — | Attributed entry-point volume, per campaign/QR/source. |
| `cta_click` | Any `TrackedLink` click | `lib/analytics.ts` (client) → `/api/track` | `{cta, topic}` | Which CTA converts, on which topic. |
| `social_click` | `/go/[slug]` for a real social network (instagram/facebook/tiktok/youtube/linkedin) | `/go/[slug]` (server) | `{platform, slug}` | Outbound social volume. |
| `whatsapp_click` | `/go/[slug]` for the whatsapp platform | `/go/[slug]` (server) | `{platform, slug}` | Is WhatsApp converting community interest. |
| `outbound_click` | **New.** `/go/[slug]` for any platform that's neither a social network nor whatsapp (spotify, a future partner/affiliate link) | `/go/[slug]` (server) | `{platform, slug}` | Was previously miscounted as `social_click` — see `classifyOutboundEvent()`. |
| `lead_submitted` | A successful `/api/lead` submission | `/api/lead` (server) | `{topic, leadId}` | Did the form convert, on what topic. |
| `contact_created` | **New.** `findOrCreateContact()` actually creates a row (not an existing match) | `/api/lead` (server) | — | Net-new people acquired, distinct from total lead volume — a returning contact submitting a second lead does NOT fire this. |
| `interest_selected` | Reserved — no multi-step form exists yet | — | — | Hook for a future qualification flow before a full lead. |
| `product_view` | **New, reserved.** No per-product page exists yet (Block 04) | — | `entity: {type:'product', id}` | Ready for Block 04's real catalog pages. |
| `offer_view` | **New, reserved.** Same as above, for a specific offer | — | `entity: {type:'offer', id}` | Same. |
| `checkout_started` / `purchase` / `subscription_started` / `subscription_cancelled` | Reserved — no checkout in this block | — | — | Funnel/revenue, once Block 04 wires commerce. |
| `event_registration` | Reserved — no RSVP flow yet | — | — | Future events feature. |

**`LEAD_CREATED` was considered and deliberately not added** — it would
be a pure synonym for `lead_submitted` (same trigger, same moment, no
distinct question it would answer that `lead_submitted` doesn't already).
Adding it would be exactly the semantic duplication the brief asked to
avoid.

## Canonical event schema

The brief's proposed shape, evaluated column by column against what
`interaction` already had (0001/0002) plus what 0003 added:

| Proposed column | Status | Where |
|---|---|---|
| `id`, `event_name`, `visitor_id`, `contact_id`, `route`, `metadata`, `created_at` | Already existed | 0001 |
| `source`, `medium`, `campaign`, `qr` | `source_id`/`campaign_id`/`qr_id` (FKs, already existed) + `medium` (**new**, raw string) | 0001 + 0003 |
| `content`, `term` | **New** | 0003 |
| `referrer` | **New** | 0003 |
| `entity_type`, `entity_id` | **New** — polymorphic, no FK possible (can point at `product` or `offer`); referential integrity is an application-layer concern, not a DB constraint, for this one pair only | 0003 |
| `session_id` | **Deliberately not added** — see below | — |

`medium`/`content`/`term`/`referrer` were already computed by
`resolveTouch()` for every event (used to derive `source_id`/
`campaign_id`/`qr_id`) and simply discarded before 0003 — persisting them
was a matter of not throwing away data already in hand, not a new
resolution path.

## Session model

Evaluated per the brief's explicit instruction to keep it minimal: **no
stored `session` table.** A session is a derived grouping over
`interaction` (gap-sessionize by `visitor_id` + a 30-minute inactivity
gap, industry-standard threshold), computed on read via SQL window
functions (`src/server/analytics/sessions.ts`). Reasoning:

- Every question the brief asks ("¿cuántas sesiones? ¿cuántos
  visitantes? ¿páginas por sesión? ¿duración? ¿primera/última página?")
  is answerable from `interaction` alone with a `lag()`/running-sum query
  — a stored table would just be a materialization of the same
  information, another place to keep in sync.
- Nothing else in the schema needs to reference a session id (no FK from
  `lead`/`orders` to a session) — if that need appears later, that's the
  moment to add a real table, not before.

## Funnels

The brief's own examples (`VISIT → LANDING_VIEW → CTA_CLICK → LEAD →
CHECKOUT_STARTED → PURCHASE`, `VISIT → TRAINING_VIEW → FACEBOOK_CLICK →
WHATSAPP_CLICK → LEAD`) aren't hardcoded — `computeFunnel()`
(`src/server/analytics/funnel.ts`) takes an ordered array of steps (a
taxonomy event name, or the special `"visit"` = any event at all) and
computes, for each step, the count of distinct visitors who reached that
step **and every step before it** (successive set intersection). Two
presets exist (`PRESET_FUNNELS`) matching the brief's own examples
exactly; a new funnel is a new array, not new architecture — this is
what "sin modificar la arquitectura fundamental" means in practice here.

"Reached a step" means "has at least one such event in range" — not
strict same-session ordering. Simple, matches the brief's own examples,
and correct at this traffic scale; a stricter definition is a query
change, not a schema change, if ever needed.

## Date ranges

One shared utility, `src/server/analytics/dateRange.ts`:
`resolveDateRange('today' | '7d' | '30d' | '90d' | {from, to})`. Every
`/api/analytics/*` route parses `?range=` (default `30d`) or an explicit
`?from=&to=` through the same `parseDateRangeParams()` — no per-endpoint
date logic. `today` means "since midnight UTC", not "the last 24 hours";
every preset is a trailing window ending now.

## Segmentation

Every read model already accepts the natural filter for its own
dimension (`getPerformanceByDimension(db, 'source'|'campaign'|'qr', range)`,
`getLeadsByDimension(db, 'source'|'campaign'|'interest', range)`) — this
block does not build a generic cross-dimension filter/segment builder
(explicitly out of scope: "No construir todavía un sistema de
segmentación complejo"). Adding a new dimension to filter by is adding a
case to these functions' existing dimension maps, not new architecture.

## Endpoint authorization

`/api/analytics/*` is business data (visitor counts, lead volume,
revenue) that must not be public, but full user authentication is
explicitly out of scope for this block too. The resolution: a
shared-secret bearer token (`ANALYTICS_API_TOKEN`,
`src/server/analytics/auth.ts`) — not a login system, just an API-key
gate suitable for an internal caller (Cristian himself, or a future
dashboard's own backend). **Fails closed**: if the token isn't
configured, every request gets 503, never an open table. Full model,
including what replaces this once real accounts exist, in
docs/SECURITY.md.

## Privacy in analytics endpoints

Every read model selects ids, slugs, labels, and aggregate counts —
never `contact.email`/`phone`/`name`. Verified by
`overview/route.integration.test.ts`, which asserts a known email/name/
phone inserted into `contact` never appears anywhere in the endpoint's
JSON response body, not just in the shape of the TypeScript types.

Two layers, both against a disposable Postgres (never real data — every
integration test file seeds its own visitors/contacts/interactions with
throwaway `@example.com` addresses):

- **Unit** (`vitest.config.mts`): `dateRange.test.ts` (range math),

- **Integration** (`vitest.integration.config.mts`, 50 tests): one file

  TikTok→/musica→CTA, YouTube→/shows, QR Aura→/entrenar→WhatsApp→lead,
  WhatsApp→/comunidad→lead, Evento→QR→/productos→product
  view→simulated purchase), run as automated, repeatable tests instead
  of manual clicking — including the real `/api/lead` route handler for
  the two lead flows, not a mock.

### Two real bugs this testing found

- **`resolveTouch()` fired three queries via `Promise.all` on a single
  shared `PoolClient`** — one Postgres connection can't run overlapping
  queries; `pg` only tolerated it via a deprecated internal queue. Fixed
  to sequential awaits (same fix applied to `computeFunnel()` and
  `getAnalyticsOverview()`, which had the same latent pattern even
  though no current caller triggers it with a single client).
- **Node-process-clock vs. Postgres-server-clock drift** in this
  sandboxed environment intermittently placed a just-committed row's
  server-clock `created_at` a few hundred ms past a range's Node-clock
  `to` bound captured moments earlier, causing flaky test failures with
  no code-correctness issue behind them. Fixed with a small forward-padded
  test-only date range helper (`testDateRange()`,
  `src/server/db/testHelpers.integration.ts`) — production code never
  needs this padding; a dashboard's "last 90 days" has no reason to
  assume a write completed milliseconds ago.
